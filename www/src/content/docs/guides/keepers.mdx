A keeper is an agent attached to a task that checks each commit the task makes. It reads the change, reports what is wrong, and hands its findings to the task's own agent to fix. When the commit is clean, the keeper goes green and stays quiet until the next one.

You keep reviewing the work, but you stop being the first one to catch the off-by-one, the missing error path or the code that does not match the project's rules. By the time you open the diff, the keepers have already been through it.

<Aside type="note">
  Keepers check **committed** work on a task's **branch**. A task in its own worktree always has one. A task in your project folder shares the checkout with your other sessions, so it takes the branch it last committed on: when one of its turns ends after making a commit on a branch other than `main` (or your base branch), that branch is the task's — and so is a commit made mid-turn, which the poll hands straight to the one session still working on it — a turn that only talks claims nothing, and a branch no task has yet goes straight to the task you used last — and keepers check it only while the checkout is on it. Switch to another branch and the **Keepers** tab says they are paused and why; switch back and they carry on. Work on `main` itself gets no keepers. Chats and Factory tasks have no keepers either. An agent that never commits gets no checks: the commit is the signal that a piece of work is ready.
</Aside>

## Add a keeper

Nothing runs until you add one. Open a task, choose the **Keepers** tab at the end of the rail, and pick **Add keeper**:

| Keeper | Looks for |
| --- | --- |
| **Review** | Bugs, regressions and unhandled edge cases introduced by the change |
| **Slop** | Code that reads as generated rather than written for its file: comments that restate the line, defensive checks on trusted paths, helpers that wrap one call |
| **Conventions** | The change checked against the project's written rules (`CLAUDE.md`, `AGENTS.md` and the invariants in `docs/adr/`) |

The menu lists these under **On every commit**. The keepers under **Before the pull request** run only when you ask — see [Before the pull request](#before-the-pull-request).

Adding one writes a two-line file into the project, such as `.warpforge/keepers/review.yaml`. Commit it and every teammate who uses Warpforge gets the same keeper. To change its model, its rounds or what it looks for, edit the file — see [Keeper files](/reference/keeper-files/).

A new keeper is on for every task in the project. The switch on each keeper turns it off, or back on, for **this task only**.

## What happens on a commit

<Steps>

1. **The task commits.** Shortly after the commit settles — or right away when the agent's turn ends — each keeper that is on starts a read-only check of the change. It cannot edit files, commit or push.

2. **The keeper reports.** A clean change turns the keeper green. Otherwise its findings appear in the Keepers tab, each with a severity and a `file:line` link.

3. **The task's agent fixes them.** All open findings, from every keeper, go to the task's agent as **one** message once it is idle and the checkout has no uncommitted changes — and, in the project folder, once no other session there is mid-turn. In the chat it shows as a compact **Keepers asked for a fix** line; click it to read the full request. Fixing is the agent's next turn in the same conversation, so the fix lands as a normal commit you can review. Findings below a keeper's `min_severity` are shown but never sent.

4. **The next commit is checked again.** Findings the fix resolved are marked fixed; anything still there goes round once more.

</Steps>

Only the task's own agent ever changes the code. A keeper never writes.

## Read the Keepers tab

Each keeper shows its state, its last ten runs and its current findings. The runs sit under **Checks per commit**, oldest on the left: a tick for a clean commit, the number of findings for one that had some — so `5 1 ✓` reads as five findings, then one, then clean.

| State | Meaning |
| --- | --- |
| **Off** | Switched off for this task |
| **Running** | Checking the latest commit |
| **Fixing** | Its findings were handed to the task's agent |
| **Waiting** | Findings are ready but the task is busy, has uncommitted changes, or is out of quota. The reason is shown underneath |
| **Green** | The latest commit is clean |
| **Findings** | The latest commit has problems |
| **Needs you** | The fixes stalled — see [When a keeper stops](#when-a-keeper-stops) |
| **Draft ready** | A keeper that writes text, such as PR-ready, finished its draft |

**The strip** is one cell per run, oldest on the left. Green is a clean run. Red is a run with findings, with the count inside. Grey is a run that settled nothing: it timed out, could not read the change, or a newer commit replaced it before it finished. Hover a cell for the run number, its commit and the result.

**Precision** under each keeper is the share of its resolved findings that were fixed rather than dismissed, with how many findings that covers. A keeper whose findings you keep dismissing is costing you more than it saves — change its instructions or switch it off.

The Keepers button on the right rail pulses grey while a keeper is checking or fixing, and turns red when a keeper has findings or needs you. Green is never a live mark: a clean keeper goes quiet. The task's row in the sidebar shows the same mark, so you can see it without opening the task.

Once the task has a pull request, its pull-request icon — in the sidebar, the task header and the task's tile in Mission Control — carries a small dot for the keepers too: red when a keeper has findings or needs you, a pulsing grey one while a keeper is checking, and none when they are all green. A keeper that needs you also puts the task in the **Needs you** queue, next to pull requests with failing checks or new comments.

## Dismiss a finding

Not every finding is right. **Dismiss** removes it from the next fix request, and you can say why. The keeper's next check is told you rejected it and not to raise it again. Dismissals count against the keeper's precision.

Click a finding's `file:line` to open it in the Explorer at that line before you decide.

## Send findings to the agent yourself

Keepers hand findings back on their own only while they still match the latest commit, so findings can be left behind — a **Check before PR** keeper's after you commit again, or a keeper's you accepted. **Send to agent** on the keeper's card sends its open findings to the task's agent as one fix request. The agent is told which commit they were found on and checks that each one still holds before fixing it. The button waits for a quiet moment: it is refused, with the reason, while the agent is working, a message of yours is queued or the worktree has uncommitted changes. A send counts as one of the keeper's fix rounds.

## When a keeper stops

A keeper does not loop forever. It stops and asks you when:

- it has used its fix rounds since its last green — three by default, set by `max_rounds` — or
- two runs in a row found as many problems or more, so the fixes are not making progress.

The keeper turns red with **Needs you** and offers three choices:

| Choice | What it does |
| --- | --- |
| **Extend** | Gives the agent more rounds. Add guidance — "keep the public API unchanged" — and it goes with the next fix request |
| **Accept** | Records the change as it is. The keeper stays quiet until the next commit |
| **Off for this task** | Switches the keeper off on this task |

Guidance is advice to the agent, not a command it must follow.

## Before the pull request

Some checks are worth running once, when the work is done, rather than on every commit. Add them from the **Before the pull request** group of **Add keeper**:

| Keeper | What it does |
| --- | --- |
| **Security** | Reports only vulnerabilities with a plausible exploit path through the changed code |
| **Thermonuclear** | Looks for complexity the change could delete rather than move: duplicated helpers, thin wrappers, oversized files. At most five findings |
| **Intent** | Compares the change with the task's brief: what was asked and not done, and what was done and not asked |
| **Verify** | Turns the task's claim into a check and runs it against the change, in the running app when one is available |
| **PR-ready** | Writes a pull request description: a TL;DR, then what changed and why, with a proposed split when the change is too big to review at once |

These keepers run in two places, always on the branch's latest commit:

- **Check before PR** in the Keepers tab header, next to **Add keeper**. It appears once the task has one of these keepers switched on, and stays disabled while one of them is still checking. Pressing it again re-runs them, even on a commit they already checked.
- **Create PR** in the push dialog. Opening the pull request form starts them once; going **Back** and returning does not start them again. The form lists each one with its state — checking, green, the number of findings, or draft ready.

Their findings go to the task's agent like any other keeper's. PR-ready's result is text, never a pass or a failure: the Keepers tab shows the draft with **Copy** and **Show all**, and when it arrives while the pull request form is open and you have not written a description, it fills the **Description** field for you. Text you typed or generated is never replaced.

Nothing here blocks you. **Create Pull Request** stays available while the keepers are checking, and you can open the pull request with findings still open.

## Pushing before the keepers are green

Keepers never block a push. When you push or create a pull request while a keeper still has findings, is still checking or is waiting for you, the dialog says which ones above its buttons — push anyway if you have decided the findings don't matter.
